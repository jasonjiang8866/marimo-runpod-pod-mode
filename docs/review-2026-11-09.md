# Review: RunPod hardware flexibility

Reviewed 2026-11-09 (Singapore), original main commit
`91c6db7200ce14d00673c9b8c078d7e1ff41b1d0`.

## Findings in the original repository

| Priority | Evidence | Impact | Resolution |
|---|---|---|---|
| High | `start.sh:20–24` selects `--no-token` when a password is absent; `:28` defaults origins to `*` | Anyone reaching the exposed editor could execute code with access to mounted files and credentials | Authentication in both edit/run modes; generated or explicit token; no wildcard origin default; `/health` remains unauthenticated |
| High | `Dockerfile:17–19` creates an isolated venv and installs only `marimo>=0.8` | The base image's PyTorch is hidden from notebook Python despite the GPU-ready claim | Install torch and marimo into the same `/opt/venv`; verify imports during build and a real operation at startup |
| Medium | `Dockerfile:2` hardcodes one RunPod PyTorch/CUDA image | No small CPU image or explicit older-driver/current-driver choice | Four versioned wheel profiles, Buildx presets, runtime GPU gate |
| Medium | `README.md` advertises Hugging Face packages, `PUBLIC_HOST`, comma-separated origins, and reproducibility | Promised dependencies/settings do not match the actual image/script | Implement host/origin settings, pin editor dependencies, document image digest and workload dependency boundaries |
| Medium | Existing notebooks are never copied into the image; volume would mask `/workspace` copies anyway | Empty mounted workspace has no shipped diagnostic | Examples stored under `/opt/marimo/examples`; opt-in non-overwriting diagnostic seeding |
| Medium | No CI, healthcheck, real CUDA check, or process supervisor | Imports, bad flags, driver failures, mount masking and child-process shutdown could go undetected | Real-CLI tests, four-image build/boot matrix, authenticated endpoint tests, health endpoint and tini process-group forwarding |
| Medium | GRPO examples use hardcoded training settings and undeclared dependencies | VRAM demand and API compatibility vary by hardware and TRL version | Preserve original experiments with explicit historical/unvalidated status; do not auto-seed or execute them |

The change removes unused SSH/nginx installs and the inherited RunPod image
startup behavior. SSH/Jupyter users must use another image or explicitly add and
configure these services; ports 22/8888 are not provided by this template.

## Version selection

Upstream releases checked: marimo 0.25.2, uv 0.13.7, PyTorch 2.15.0. CPU and
CUDA 13.2 use current torch; CUDA 12.6 uses 2.14.1; CUDA 12.8 uses 2.11.0 because
those wheel families were discontinued in newer torch series. Versions are
selected explicitly, not inferred from the machine performing the Docker build.

## Validation boundaries

The regression suite uses installed marimo 0.25.2 and PyTorch 2.15.0+cpu, not a
mock CLI. It exercises real HTTP authentication/health, generated tokens, fixed
tokens via stdin/file, proxy/base path, app mode, CPU autograd, missing-GPU
failure, invalid configuration and preservation of user notebooks. A mocked MIG
property test validates the insufficient-memory error path only; it is not GPU
execution evidence.

The added CI builds and boots every image profile on CPU-hosted runners. These
jobs explicitly set `REQUIRE_GPU=0`. Docker/GPU checks must be distinguished:
image import/HTTP success does not prove CUDA kernel compatibility.

Real RunPod allocation, CUDA execution, MIG behavior, public proxy/WebSockets,
GPU costs and resource cleanup are **not verified** by this review. No paid Pod
is launched. A later authorized GPU smoke should capture digest, driver, visible
hardware, startup operation results and independent cleanup evidence.

Full historical GRPO/LoRA notebook modernization (model choice, current TRL APIs,
locked workload stack, training quality and memory benchmarks) is separate work.
This PR supplies a reliable notebook runtime on which to perform it.
